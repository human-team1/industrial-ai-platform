

# 팀 프로젝트 개발 컨벤션

## 1. 목적

   본 문서는 웹 서비스 팀 프로젝트 진행 시 협업 효율을 높이고, 코드 및 문서의 일관성을 유지하기 위한 기본 규칙을 정의한다. 팀원은 아래 규칙을 공통 기준으로 삼아 개발 및 작업 공유를 진행한다.

---

## 2. 협업 방식

### **2.1 기본 개발 흐름**

- 개발은 **기능 단위**로 진행한다.
- 기능별로 작성된 **Backlog**를 기준으로 담당자가 해당 기능을 처음부터 끝까지 책임지고 개발한다.
- 하나의 기능은 가능한 범위 내에서 **한 담당자가 end-to-end로 개발**하는 것을 원칙으로 한다.
- 기능 개발 시 **Frontend UI - API 연동 - 포트 생성 - 비즈니스 로직 작성**까지 전체 흐름을 연결하여 진행한다.
- 모든 작업은 **별도 브랜치에서 개발**하고, 완료 후 **Pull Request(PR)** 를 생성한다.
- 코드 리뷰가 완료되면 **코드 리뷰자가 `develop` 브랜치로 병합한다.**

### 2.2 Jira 작업 관리 기준

- 작업 진행 상황과 담당 업무는 **Jira**를 기준으로 관리한다.
- **Epic**은 요구사항 명세를 기준으로 한 **큰 기능 단위**로 정의한다.
- **Task**는 Epic을 실제 구현 가능한 **작업 단위**로 분리한 이슈로 정의한다.
- **Bug**는 기능 오동작, 예외 발생, 요구사항과 다른 동작을 수정하기 위한 **이슈**로 정의한다.
- **Epic**은 팀장 또는 기능 단위 책임자가 생성하고, **Task**와 **Bug**는 담당자가 직접 생성하거나 팀 내 합의된 방식에 따라 등록한다.
- **Task**는 우선순위에 따라 **Backlog**에 등록하고, 우선순위가 높은 작업부터 진행한다.
- 필요 시 **Task**는 **Sub-task**로 세분화할 수 있다.
- 담당자는 자신이 맡은 **Jira 이슈의 상태**를 직접 업데이트한다.

### 2.3 작업 및 진행 상황 공유

- **작업 시작 전** **Jira 이슈를 생성하거나 담당 이슈를 확인**한다.
- **작업 진행 중**에는 **Jira 상태**를 **현재 진행 상황에 맞게 업데이트**한다.
- **작업 완료 후**에는 관련 **PR**과 함께 **진행 상황을 공유**한다.
- 작업 내용, 변경 범위, 특이사항은 **Jira**와 **PR 본문**에 함께 정리한다.
- 팀원이 확인해야 하는 변경 사항은 **Slack** 또는 **Notion**을 통해 추가로 공유한다.

### 2.4 커뮤니케이션 채널

- **Slack** : 공지사항 공유, 빠른 확인, 일정 조율, 간단한 질문
- **GitHub PR** : 코드 리뷰, 수정 요청, 구현 관련 논의
- **Jira** : 회의록, 작업 상태 관리, 담당자 및 진행 현황 공유
- **Notion** : 컨벤션, 기능 명세, 프로젝트 문서 정리

## 3. Git 브랜치 전략

### 3.1 브랜치 운용 규칙

- `main` 브랜치에는 직접 push하지 않는다.
- 모든 작업은 `develop` 브랜치에서 분기한 작업 브랜치에서 진행한다.
- 작업 완료 후 PR을 생성하고, 코드 리뷰 완료 후 코드 리뷰자가 `develop` 브랜치로 병합한다.
- 최종 배포 또는 제출 시 `develop`에서 `main`으로 병합한다.

### 3.2 브랜치 종류

- **`main`** : 최종 배포 또는 제출 가능한 안정 브랜치
- **`develop`** : 개발 통합 브랜치
- **`feat/기능명`** : 새로운 기능 개발
- **`fix/버그명`** : 버그 수정
- **`refactor/기능명`** : 리팩토링
- **`docs/문서명`** : 문서 작업
- **`chore/작업명`** : 설정, 의존성, 빌드 등 기타 작업
- **`test/작업명`** : 테스트 코드 작성 및 수정
- **`hotfix/작업명`** : 운영 중 긴급 수정
- **`release/버전명`** : 배포 전 최종 점검 및 버전 관리

### 3.3 형식 및 예시

- 브랜치 이름은 **`작업유형/작업내용`** 형식으로 작성한다.
- **`feat/login-page`** : 로그인 페이지 기능 개발
- **`fix/signup-validation`** : 회원가입 유효성 검사 오류 수정
- **`refactor/user-service`** : 사용자 서비스 로직 리팩토링

## 4. 커밋 메시지 규칙

### 4.1 규칙

- 커밋 메시지는 변경 내용을 한눈에 파악할 수 있도록 작성한다.
- 하나의 커밋에는 하나의 작업만 담는 것을 원칙으로 한다.

### 4.2 형식

- 커밋 메시지는 **`type: 작업 내용`** 형식으로 작성한다.

### 4.3 종류

- **`feat`** : 기능 추가
- **`fix`** : 버그 수정
- **`docs`** : 문서 수정
- **`refactor`** : 리팩토링
- **`test`** : 테스트 코드 추가 및 수정
- **`chore`** : 빌드 설정, 패키지 설치, 환경 설정 관련 작업

### 4.4 예시

- **`feat: 로그인 API 연동`**
- **`fix: 회원가입 유효성 검사 오류 수정`**
- **`refactor: AI 요청 서비스 분리`**

## 5. Pull Request 규칙

### 5.1 PR 생성 기준

- 모든 기능 개발 및 수정 작업은 브랜치 단위로 진행한 뒤 PR을 생성한다.
- PR은 가능한 한 **기능 단위**로 작성한다.
- 너무 큰 단위의 변경은 지양하고, 리뷰 가능한 크기로 나누어 올린다.

### 5.2 형식 및 예시

- PR 제목은 **`[type] 작업 내용`** 형식으로 작성한다.
- 예시
    - **`[feat] 로그인 기능 구현`**
    - **`[fix] 회원가입 유효성 검사 오류 수정`**

### 5.3 PR 본문 포함 항목

- PR 본문에는 아래 내용을 최소한으로 포함한다.
    - 관련 작업
    - 작업 내용
    - 주요 변경 사항
    - 테스트/검증 내용
    - 참고 사항
    - UI 변경이 있는 경우 스크린샷 첨부 권장

### 5.4 체크사항

- PR 생성 전 아래 사항을 확인한다.
    - **현재 작업 브랜치**가 올바른지 확인한다.
    - 불필요한 코드, 주석, 콘솔 로그를 제거한다.
    - **커밋 메시지**를 규칙에 맞게 **작성**한다.
    - **변경 사항을 PR 본문에 정리**한다.
    - 기능이 정상 동작하는지 직접 **테스트**한다.
    - 민감 정보(.env, API Key 등)가 포함되지 않았는지 확인한다.
    - merge 충돌 가능성이 없는지 확인한다.

### 5.5 **PR 본문 예시**

```markdown
## 관련 작업
- 

## 작업 내용
-

## 주요 변경 사항
-

## 테스트/검증 내용
- [ ] 기능 동작 확인
- [ ] 예외 케이스 확인
- [ ] 추가 확인 필요

## 참고 사항
-
```

## 6. 프로젝트 구조 원칙

### 6.1 규칙

- 프로젝트는 **Frontend / Spring Backend / FastAPI AI Server / Data Infra** 구조를 따른다.
- 구조는 **헥사고날 아키텍처** 기반을 지향한다.
- 각 계층은 역할과 책임에 따라 분리한다.

### 6.2 계층 구분

- **`domain`** : 핵심 비즈니스 로직
- **`application`** : 유스케이스, 서비스 흐름
- **`infrastructure`** : DB, 외부 API, 구현체
- **`presentation`** : API, Controller, Router, UI 진입점

### 6.3 역할 원칙

- **Controller / Router** : 요청·응답 처리
- **Service / UseCase** : 비즈니스 로직 처리
- **Repository / Adapter** : 데이터 접근 및 외부 연동

## 7. API 설계 규칙

### 7.1 규칙

- API는 **RESTful** 형식을 따른다.
- URL은 **명사 중심**으로 작성한다.
- 컬렉션 경로는 **복수형**을 사용한다.
- 동작은 URL보다 **HTTP 메서드**로 표현한다.
- 요청 및 응답 형식은 프론트엔드와 백엔드가 공통으로 이해할 수 있도록 일관되게 유지한다.

### 7.2 예시

- **`GET /users`**
- **`GET /posts/{id}`**
- **`POST /posts`**
- **`PATCH /posts/{id}`**
- **`DELETE /posts/{id}`**

### 7.3 성공 응답 원칙

- 성공 응답 형식은 가능한 한 일관되게 유지한다.
- 성공 여부, 데이터, 메시지 구조를 통일한다.
- 목록 조회, 단건 조회, 생성, 수정, 삭제 응답도 동일한 원칙 안에서 설계한다.

**예시**

```json
{
  "success": true,
  "data": {},
  "message":"요청이 성공적으로 처리되었습니다."
}
```

### 7.4 에러 응답 형식

- 에러 응답은 **RFC 9457 Problem Details** 형식을 기본으로 사용한다.
- 기본 필드는 아래와 같이 정의한다.
    - **`type`** : 에러 유형을 식별하기 위한 값
    - **`title`** : 에러의 제목 또는 요약 설명
    - **`status`** : 해당 응답의 HTTP 상태 코드
    - **`detail`** : 에러에 대한 구체적인 설명
    - **`instance`** : 에러가 발생한 요청 경로 또는 리소스 식별 값
- 필요 시 **`errorCode`**, **`errors`** 등의 확장 필드를 추가할 수 있다.
- 유효성 검증 오류가 여러 개일 경우 **`errors`** 배열로 세부 항목을 전달한다.
- 모든 실패 응답은 가능한 한 동일한 JSON 구조를 사용한다.

**예시**

```json
{
  "type":"https://api.example.com/problems/validation-error",
  "title":"Validation failed",
  "status": 422,
  "detail":"요청 값이 올바르지 않습니다.",
  "instance":"/api/v1/users/signup",
  "errorCode":"VALIDATION_ERROR",
  "errors": [
    {
      "field":"email",
      "reason":"올바른 이메일 형식이 아닙니다."
    }
  ]
}
```

### 7.5 공통 예외 처리 규칙

- 예외 처리는 가능한 한 **전역 예외 처리 방식**으로 일괄 처리한다.
- Controller/Router 또는 Service마다 예외 응답을 제각각 작성하지 않는다.
- 예상 가능한 예외는 명확한 메시지와 적절한 **HTTP 상태 코드**로 응답한다.
- 예상하지 못한 서버 내부 예외는 사용자에게 일반적인 오류 메시지를 반환하고, 상세 원인은 서버 로그를 통해 확인한다.
- 내부 구현 정보, 스택 트레이스, 민감한 서버 정보는 응답 본문에 직접 노출하지 않는다.
- 프론트엔드가 예외 상황을 일관되게 처리할 수 있도록 에러 응답 구조를 통일한다.

### 7.6 상태 코드 기준

- HTTP 상태 코드는 의미에 맞게 사용한다.
- 동일한 상황에서는 동일한 상태 코드를 사용하여 일관성을 유지한다.

**기준 예시**

- **`200 OK`** : 조회, 수정, 처리 성공
- **`201 Created`** : 리소스 생성 성공
- **`204 No Content`** : 성공했지만 응답 본문이 필요 없는 경우
- **`400 Bad Request`** : 잘못된 요청 형식, 필수 값 누락, 잘못된 파라미터
- **`401 Unauthorized`** : 인증이 필요하거나 인증 정보가 유효하지 않은 경우
- **`403 Forbidden`** : 인증은 되었지만 권한이 없는 경우
- **`404 Not Found`** : 요청한 리소스를 찾을 수 없는 경우
- **`409 Conflict`** : 현재 리소스 상태와 충돌하는 요청인 경우
- **`422 Unprocessable Content`** : 요청 형식은 맞지만 의미상 처리할 수 없거나 유효성 검증에 실패한 경우
- **`500 Internal Server Error`** : 서버 내부 처리 중 예기치 못한 오류가 발생한 경우

## 8. 코드 컨벤션

### 8.1 공통 원칙

- 가독성을 우선으로 한다.
- 중복 코드는 줄이고 공통 로직은 분리한다.
- 변수명, 함수명, 메서드명, 클래스명은 **이름만 보고 역할과 의미를 파악할 수 있도록 작성**한다.

### 8.2 네이밍 규칙

- **Python 변수/함수명** : `snake_case`
- **Java 변수/메서드명** : `camelCase`
- **클래스명** : `PascalCase`
- **상수명** : `UPPER_SNAKE_CASE`

### 8.3 이름 작성 원칙

- 변수명은 의미가 드러나는 **명사형**으로 작성한다.
- 함수명/메서드명은 동작이 드러나는 **동사형**으로 작성한다.
- Boolean 값은 is, has, can 등 **상태가 드러나는 형태**로 작성한다.
- 상수명은 고정된 값임을 알 수 있도록 **대문자와 언더스코어 형식**으로 작성한다.
- 의미 없는 축약어와 모호한 이름은 지양한다.

**좋은 예시**

- **변수명**: `user_name`, `documentList`, `search_result`
- **함수명**: `get_user_info()`, `createDocument()`, `update_user_status()`
- **Boolean**: `is_active`, `hasPermission`, `can_retry`
- **상수명**: `DEFAULT_TIMEOUT`, `MAX_FILE_SIZE`

### 8.4 주석 규칙

- 주석은 “무엇”보다 “왜”를 설명한다.
- 임시 구현이나 추후 수정이 필요한 부분은 `TODO`, `FIXME` 로 표시한다.
- `TODO`는 향후 추가 구현, 개선, 리팩토링이 필요한 경우에 사용한다.
- `FIXME`는 현재 동작상 문제가 있거나 수정이 필요한 경우에 사용한다.

**예시**

```java

// TODO: 로그인 실패 횟수 제한 기능 추가
// FIXME: 잘못된 예외 메시지가 반환되는 문제 수정 필요
```

## 9. 기타 규칙

### 9.1 개발 환경 문서화

- 개발 환경 설정 방법은 각 시스템의 README에 작성한다.
- README에는 프로젝트 실행 방법, 필수 설치 항목, 환경 변수, 의존성 설치 방법 등을 포함한다.
- 개발 환경 관련 내용은 변경 시 즉시 수정하여 최신 상태를 유지한다.
- 기능 개발로 인해 실행 방식, 환경 변수, 의존성, 실행 순서가 변경되면 README를 함께 수정한다.
- 팀원들이 개발 환경 구성에 불필요한 시간을 쓰지 않도록 문서를 지속적으로 보완한다.

### 9.2 보안 및 민감 정보 관리

- .env 파일 및 민감 정보는 업로드하지 않는다.
- API Key, 비밀번호, 토큰, 인증 정보는 코드나 문서에 직접 작성하지 않는다.

### 9.3 공통 설정 및 라이브러리 변경

- 라이브러리 설치 및 설정 변경 시 팀원과 공유한다.
- 공통 설정 파일 변경 시 반드시 팀원에게 알린다.
- 의존성이나 실행 방법이 바뀌는 경우 README도 함께 수정한다.

### 9.4 제출 전 점검

- 불필요한 콘솔 로그는 제출 전 제거한다.
- 디버깅용 코드, 임시 파일, 사용하지 않는 주석은 정리한다.
- 기능 동작 여부와 주요 예외 상황을 최소 1회 이상 점검한다.
