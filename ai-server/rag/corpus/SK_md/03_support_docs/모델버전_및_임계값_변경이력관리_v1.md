# 모델 버전 및 임계값 변경이력관리

샘플 매뉴얼 v1

산업 이미지 이상탐지 프로젝트 - RAG/LLM 문서셋

## 1. 문서 목적

본 문서는 산업 이미지 이상탐지 프로젝트에서 사용되는 AI 모델 버전과 anomaly score threshold(임계값)의 변경 이력을 일관되게 기록하고 관리하기 위한 기준을 설명한다.

본 프로젝트는 이미지 업로드 검사와 실시간 검사를 통해 anomaly score, 정상/재검사/불량 의심 판정, heatmap/anomaly map을 제공한다. 같은 이미지라도 모델 버전이나 threshold 설정에 따라 결과가 달라질 수 있으므로, 모든 검사 결과에는 당시 적용된 모델 버전과 threshold 설정 정보를 함께 남겨야 한다.

이 문서는 모델 교체, threshold 조정, 배포, 롤백 과정에서 승인 및 검증 기준을 명확히 하고, 결과 상세, 운영 모니터링, 감사 로그, 재검토 기능에서 동일한 기준으로 변경 내역을 확인할 수 있도록 하는 것을 목적으로 한다.

## 2. 적용 범위

| 항목 | 내용 |
| --- | --- |
| 적용 기능 | 이미지 업로드 검사, 실시간 검사, 결과 상세, 설정, 운영 모니터링, RAG 기반 문서 질의응답 |
| 적용 대상 | 모델 버전, threshold, 검사 결과 적용값, 배포/롤백 상태, 변경 이력 |
| 적용 사용자 | 일반 사용자, 관리자, 시스템 |
| 관련 결과 | anomaly score, 판정 결과, model version, threshold profile, heatmap/anomaly map, result artifact |
| 연계 문서 | 정상_재검사_불량_판정기준서_v1, 이상감지_작업자대응절차_SOP_v1, 오탐_미탐_발생보고서_양식_v1 |

일반 사용자는 허용 범위 내 개인 threshold 설정을 변경할 수 있다.
관리자는 모델 버전, 기본 threshold 정책, 적용 범위, 변경 이력, 배포/롤백 상태를 관리한다.
시스템은 검사 결과에 적용된 모델 버전과 threshold 정보를 자동 저장한다.

본 문서는 모델 학습 코드의 상세 구현이나 운영 서버 인프라 배포 절차 전체를 정의하지 않는다. 다만 모델 버전 또는 threshold 변경이 검사 결과, 챗봇 설명, 운영 보고서에 영향을 주는 경우에는 본 문서의 기준을 적용한다.

## 3. 변경 관리 대상

변경 관리 대상은 크게 모델 버전, threshold, 검사 결과 적용값, 배포/롤백 상태로 구분한다.

| 관리 대상 | 설명 | 주요 기록 정보 |
| --- | --- | --- |
| 모델 버전 | 이상탐지에 사용되는 모델 또는 모델 설정 버전 | 모델명, 버전, backbone, 적용 카테고리, 성능 지표, 배포 상태 |
| threshold | 정상/재검사/불량 의심을 나누는 anomaly score 기준 | threshold 값, 재검사 구간, 적용 범위, 변경 사유, 변경자 |
| 검사 결과 적용값 | 검사 당시 사용된 모델과 threshold 정보 | 검사 ID, model version, threshold profile, anomaly score, 판정 결과 |
| 배포/롤백 상태 | 모델 운영 반영 및 복구 상태 | 배포일, 배포자, 롤백 여부, 영향 범위, 후속 조치 |

모델 버전과 threshold 변경 이력은 검사 결과 재현성, 판정 기준 추적, 운영 감사에 필요한 정보이다. 실제 DB 테이블 및 필드 연계는 부록의 DB/ERD 연계 참고 항목에서 관리한다.

## 4. 모델 버전 변경 이력 관리

모델 버전이 새로 등록되거나 운영에 반영될 때는 아래 항목을 기준으로 변경 이력을 기록한다. 모델 변경은 anomaly score 산출 방식 자체에 영향을 줄 수 있으므로 운영 반영 전 검증과 승인 절차를 거쳐야 한다.

| 기록 항목 | 설명 |
| --- | --- |
| 변경 ID | 모델 변경 이력 식별자 |
| 모델명 | 모델 이름 또는 모델 계열 |
| 이전 버전 | 변경 전 운영 버전 |
| 신규 버전 | 변경 후 적용 예정 또는 적용된 버전 |
| 적용 카테고리 | object/texture 또는 특정 카테고리 |
| 주요 변경 내용 | backbone, feature layer, coreset, memory bank, 입력 해상도 등 변경 요약 |
| 주요 성능 지표 | Image AUROC, Pixel AUROC, PRO, F1-score, inference time, GPU memory 등 |
| 검증 데이터 | 성능 확인에 사용한 데이터셋 또는 카테고리 |
| 변경 사유 | 성능 개선, 속도 개선, 오탐/미탐 개선, 배포 환경 대응 등 |
| 승인자 | 운영 반영 승인자 |
| 배포 상태 | 배포 대기, 운영 중, 비활성, 롤백 등 |
| 확인 항목 | 기준 |
| --- | --- |
| 모델 파일 존재 여부 | 모델 가중치 또는 배포 파일이 저장소에 존재해야 한다. |
| 모델 버전 중복 여부 | 동일 모델에 같은 버전명이 중복 등록되지 않아야 한다. |
| 검증 지표 입력 여부 | 운영 반영 전 주요 성능 지표가 입력되어야 한다. |
| 배포 상태 | 검증 전 모델은 운영 중 상태가 될 수 없다. |
| 결과 추적성 | 신규 검사 결과에는 변경된 model_version 정보가 저장되어야 한다. |
| 롤백 가능성 | 신규 모델 적용 전 직전 안정 버전을 확인해야 한다. |

## 5. threshold 변경 이력 관리

threshold는 정상/재검사/불량 의심 판정에 직접 영향을 주므로 변경 전후 값, 변경 사유, 변경자, 적용 시점을 반드시 기록한다. 현장 작업자는 threshold를 임의로 변경하지 않는다. 단, 일반 사용자는 관리자가 정한 허용 범위 내에서 개인 threshold를 변경할 수 있으며, 관리자는 회사별 또는 설비별 기본 threshold와 허용 범위를 관리한다. 모든 threshold 변경 이력은 변경 전 값, 변경 후 값, 변경자, 적용 범위, 변경 시각과 함께 저장한다.

| 기록 항목 | 설명 |
| --- | --- |
| 변경 ID | threshold 변경 이력 식별자 |
| 적용 범위 | 전체, 카테고리, 설비, 사용자 등 |
| 이전 threshold | 변경 전 기준값 |
| 신규 threshold | 변경 후 기준값 |
| 재검사 구간 | 정상/재검사/불량 의심 경계 구간 |
| 변경 사유 | 오탐 감소, 미탐 감소, 재검사율 조정 등 |
| 변경자 | 변경 수행자 |
| 승인 여부 | 승인 필요/불필요 또는 승인 완료 여부 |
| 적용 시점 | 즉시 적용 또는 다음 검사부터 적용 |
| 비고 | 추가 참고 사항 |
| 확인 항목 | 기준 |
| --- | --- |
| 허용 범위 검증 | 신규 threshold는 허용 최소값 이상, 허용 최대값 이하여야 한다. |
| 값 형식 검증 | 숫자 형식이어야 하며 null 또는 문자열은 허용하지 않는다. |
| 판정 관계 검증 | 저신뢰/재검사 구간과 불량 의심 구간의 관계가 정책에 맞아야 한다. |
| 변경 사유 입력 | 변경 사유는 필수 또는 강력 권장 항목으로 관리한다. |
| 변경 이력 저장 | 이전 값, 신규 값, 변경자, 변경 시각을 저장해야 한다. |
| 신규 검사 적용 | 변경된 값은 저장 이후 신규 검사부터 적용한다. |
| 기존 결과 처리 | 기존 결과는 기본적으로 재계산하지 않으며, 필요 시 별도 재처리 이력으로 관리한다. |

## 6. 검사 결과에 반드시 저장해야 하는 정보

검사 결과는 단순히 anomaly score와 판정 결과만 저장하면 안 된다. 결과가 생성된 시점의 모델과 threshold를 함께 저장해야 나중에 결과를 재현하거나 판정 근거를 설명할 수 있다.

| 기록 항목 | 설명 |
| --- | --- |
| 검사 ID | 어떤 검사 결과인지 식별하는 ID |
| 카테고리 | 검사 대상 카테고리 |
| anomaly score | 모델이 산출한 이상 점수 |
| 판정 결과 | 정상, 재검사, 불량 의심 |
| 추가 상태/사유 | 저신뢰, 반복 감지, 촬영 조건 의심 등 판정 보조 상태 |
| 모델 버전 | 검사 당시 사용된 모델 버전 |
| threshold 설정 정보 | 적용된 threshold profile 또는 설정 ID |
| heatmap artifact | heatmap/anomaly map 저장 위치 |
| 결과 생성 시각 | 검사 결과가 생성된 시각 |

RAG/LLM이 결과 설명을 제공할 때 “왜 이 결과가 재검사인가?”, “어떤 모델로 검사했나?”, “threshold가 바뀐 뒤 결과가 달라졌나?”와 같은 질문에 답하려면 위 정보가 반드시 저장되어야 한다.

## 7. 변경 승인 및 검증 기준

모델 버전 변경과 threshold 변경은 영향 범위가 다르므로 승인 기준을 분리한다.

| 변경 유형 | 수행 주체 | 승인 기준 |
| --- | --- | --- |
| 개인/실험용 threshold 변경 | 일반 사용자 | 관리자가 설정한 허용 범위 내 변경 |
| 카테고리별 threshold 변경 | 관리자 | 검증 결과와 변경 사유 필요 |
| 회사/서비스 기본 threshold 변경 | 관리자 | 오탐/미탐 영향 검토 필요 |
| 허용 범위 변경 | 관리자 | 사용자 설정 가능 범위 변경 이력 필요 |
| 기존 결과 재계산 | 관리자 | 별도 재처리 이력과 감사 로그 필요 |
| 검증 항목 | 기준 |
| --- | --- |
| 성능 검증 | 기존 모델 대비 주요 지표가 유지 또는 개선되어야 한다. |
| 속도 검증 | 실시간 또는 업로드 분석 기준 응답시간을 충족해야 한다. |
| 시각화 검증 | heatmap/anomaly map이 정상 생성되어야 한다. |
| 결과 저장 검증 | model version과 threshold 설정 정보가 결과에 저장되어야 한다. |
| 운영 승인 | 관리자가 운영 반영을 승인해야 한다. |
| 롤백 가능성 | 이전 안정 버전으로 복구 가능해야 한다. |

## 8. 배포 후 모니터링 및 롤백 기준

모델 변경 또는 주요 threshold 변경 후에는 일정 기간 동안 운영 지표를 확인한다.

| 모니터링 항목 | 확인 내용 |
| --- | --- |
| 이상 판정 비율 | 변경 전 대비 불량 의심 또는 이상 판정 비율이 급격히 증가/감소했는지 확인한다. |
| 재검사 비율 | 저신뢰/경계 구간 결과가 과도하게 증가했는지 확인한다. |
| 오탐/미탐 보고 | 작업자 보고 사례 또는 재검토 요청이 증가했는지 확인한다. |
| 평균 응답 시간 | 실시간 검사 또는 업로드 검사 응답 시간이 악화됐는지 확인한다. |
| 결과 저장 오류 | 원본 이미지, heatmap, 결과 JSON/CSV 등 artifact 저장 실패 여부를 확인한다. |
| 사용자 피드백 | 현장 작업자의 불편 또는 이상 보고가 있는지 확인한다. |

신규 모델 또는 threshold 적용 후 검사 실패율 증가, 오탐/미탐 급증, heatmap 생성 오류, 응답시간 초과, 현장 작업자 심각 이슈 보고가 발생하면 이전 안정 버전으로 롤백을 검토한다.

| 롤백 기록 항목 | 설명 |
| --- | --- |
| 롤백 대상 모델 | 문제가 발생한 신규 모델 버전 |
| 복구 모델 | 이전 안정 모델 버전 |
| 롤백 사유 | 장애, 성능 저하, 오판정 증가 등 |
| 롤백 수행자 | 관리자 또는 시스템 관리자 |
| 롤백 시각 | 롤백 처리 시각 |
| 영향 범위 | 영향을 받은 검사 유형, 설비, 사용자 |
| 후속 조치 | 재검증, 모델 비활성화, 재학습 후보 등록 등 |

## 9. 작업자/관리자 권한 기준

| 역할 | 가능 작업 | 제한 사항 |
| --- | --- | --- |
| 현장 작업자 | 결과 확인, 재검사 요청, 오탐/미탐 보고 | 모델 버전 직접 변경 불가 |
| 일반 사용자 | 허용 범위 내 개인 threshold 설정 변경, 결과 확인, 문서/RAG 질의 | 허용 범위 밖 threshold 변경 및 모델 배포 불가 |
| 관리자 | 모델 버전 등록/검증, 회사·설비별 threshold 정책 관리, 배포/롤백 판단, 변경 이력 확인 | 변경 사유와 이력 기록 필요 |
| 시스템 | 검사 결과에 model version, threshold profile, anomaly score, 판정 결과를 자동 저장 | 임의 변경 불가, 정책에 따라 자동 처리 |

모델, threshold, 성능 관련 문서에서도 별도 역할명을 추가하지 않고 관리자 중심으로 안내한다. 필요한 경우 관리자의 검토 범위를 모델 버전, threshold, 성능 지표, 배포/롤백으로 구체화한다.

## 10. 결과 화면 및 RAG 연계 기준

결과 상세 화면에는 anomaly score, 판정 결과, model version, threshold 설정 정보, heatmap/anomaly map, result artifact가 함께 표시되는 것이 바람직하다.

RAG/LLM은 결과 설명 시 모델 버전 및 threshold 이력 정보를 직접 계산하지 않는다. 다만 사용자가 “왜 이 결과가 재검사인가?”, “어떤 모델로 검사했나?”, “threshold가 바뀐 뒤 결과가 달라졌나?”와 같이 질문할 경우, 저장된 model version과 threshold profile 정보를 근거로 설명할 수 있다.

| 질문 유형 | 필요한 근거 정보 |
| --- | --- |
| 왜 재검사인가? | anomaly score, threshold profile, heatmap 위치, 판정 기준 문서 |
| 어떤 모델로 검사했나? | model version, 모델명, 배포 상태 |
| threshold 변경 후 결과가 달라졌나? | 이전/신규 threshold, 적용 시점, 검사 생성 시각 |
| 모델 변경 후 오탐이 늘었나? | 오탐/미탐 보고서, 모니터링 지표, 변경 이력 |

## 11. 예상 질문

모델 버전은 왜 검사 결과마다 저장해야 하나?

threshold를 바꾸면 기존 검사 결과도 자동으로 바뀌나?

현장 작업자가 threshold를 직접 변경할 수 있나?

모델 버전 변경 전에는 어떤 검증이 필요한가?

모델 변경 후 문제가 생기면 어떻게 처리하나?

결과 상세 화면에는 어떤 모델/threshold 정보가 보여야 하나?

threshold 변경 이력이 RAG 답변에 필요한 이유는 무엇인가?

threshold 변경 사유는 꼭 입력해야 하나?

모델 성능 지표는 어떤 것을 저장해야 하나?

모델 변경과 threshold 변경 중 어떤 것이 더 운영 리스크가 큰가?

## 13. 참고 및 비고

본 문서는 산업 이미지 이상탐지 프로젝트의 RAG/LLM 샘플 문서셋 구축을 위해 작성한 운영형 샘플 매뉴얼이다.

구체적인 모델 성능 수치와 threshold 값은 모델 실험 결과 및 운영 설정 파일에서 별도 관리한다.

실제 DB 테이블명과 필드명은 구현 단계에서 변경될 수 있다.

## 부록. DB/ERD 연계 참고

아래 내용은 구현 단계에서 참고할 수 있는 DB/ERD 연계 정보이다. 본문 운영 기준과 실제 테이블명은 구현 환경에 따라 달라질 수 있다.

| 테이블 | 관리 목적 |
| --- | --- |
| MODEL | 모델명, 모델 유형 관리 |
| MODEL_VERSION | 모델 버전, 성능 지표, 파일 정보 관리 |
| MODEL_DEPLOYMENT | 모델 배포 및 롤백 이력 관리 |
| USER_THRESHOLD | 현재 활성 threshold 설정 관리 |
| USER_THRESHOLD_HISTORY | threshold 변경 이력 관리 |
| INSPECTION_RESULT | 검사 당시 모델/threshold/score 저장 |
| AUDIT_LOG | 변경자, 변경 시각, 변경 전후 값 기록 |
| 보완 권장 사항 | 이유 |
| --- | --- |
| USER_THRESHOLD에 threshold_version 추가 | 현재 활성 threshold의 버전을 명확히 구분하기 위해 필요 |
| USER_THRESHOLD_HISTORY에 old/new low confidence threshold 추가 | 저신뢰/재검사 임계값 변경 전후 값을 추적하기 위해 필요 |
| USER_THRESHOLD_HISTORY에 apply_scope 추가 | 사용자/설비/검사 대상 중 어떤 범위에 적용됐는지 추적하기 위해 필요 |
| USER_THRESHOLD_HISTORY에 changed_reason_code 추가 | 변경 사유를 표준 코드로 관리하기 위해 선택적으로 필요 |
